# JSONL出力フォーマット

*English: [JSONL_FORMAT.md](JSONL_FORMAT.md)*

STD-42デコーダプラグインは、デコードした呼出しを
[JSON Lines](https://jsonlines.org/)（JSONL）形式で2つのシンクへ出力できます。

- **ファイル** — 指定パスに追記し、1行ごとにフラッシュします。
- **TCP** — `127.0.0.1` の指定ポートに接続している全クライアントへ配信します。

両シンクが出力する**行の内容は同一**です。各シンクはレコードごとに `\n` を1つ
付加します。レコード自体に生の改行は含まれません（ペイロード中の改行はエスケープ
されます。[エンコーディング](#エンコーディング)参照）。

シリアライザは [`src/sink/call_json.cpp`](../src/sink/call_json.cpp) の
`serialize_call` です。

## 行が出力されるタイミング

**呼出し1件につき1行**、すなわちアドレスコードワードに続くメッセージが完結した
時点で出力されます。呼出しは、次のアドレスコードワードが来たとき、アイドルコード
ワードが来たとき（RCR STD-42 §3.4.4）、またはフレーム同期を失ったときに終了します。

- メッセージコードワードが後続しないアドレスコードワードも1行出力されます。
  `text` は空、`payload_bits` は0で、いわゆるトーンのみの呼出しです。
- アイドルコードワード自体は行を生成しません。パネルで件数が数えられるだけです。
- 訂正不能なコードワードを取りこぼした呼出しも出力され、`bad_codewords` が1以上に
  なります。その場合 `text` は欠落を含むものとして扱ってください。
- パネルで**アドレスフィルタ**を設定している場合、対象外アドレスへの呼出しは
  一切出力されません。

## レコードのスキーマ

各行は単一のJSONオブジェクトです。フィールドの順序は安定していますが、順序に依存
しない実装を推奨します。

| フィールド            | 型      | 常時? | 説明 |
|-----------------------|---------|-------|------|
| `rx_time_ms`          | number  | はい  | デコード時点の受信機の時刻。Unixエポックからのミリ秒（UTC）。 |
| `rx_time`             | string  | はい  | 同じ時刻のISO-8601 UTC表記 `YYYY-MM-DDThh:mm:ss.sssZ`。 |
| `address`             | number  | はい  | 21ビットの受信機アドレス（0〜2097151）。コードワード中の18ビットと、そのコードワードが載っていたフレーム番号から再構成します（§3.3）。 |
| `function`            | number  | はい  | ファンクションビット 0〜3（§3.4.2）。 |
| `function_label`      | string  | はい  | 同じ値を `"A"`〜`"D"` で表したもの。 |
| `frame`               | number  | はい  | アドレスコードワードが載っていたフレーム 0〜7。`address & 7` に等しくなります。 |
| `baud`                | number  | はい  | デコードに成功した伝送速度。`512`、`1200`、`2400` のいずれか。 |
| `inverted`            | boolean | はい  | 同期コードワードが補数側と一致した場合 `true`。受信経路で極性が反転していることを示します。 |
| `format`              | string  | はい  | 実際に適用したメッセージ形式。`"Numeric"` / `"Alphanumeric"` / `"Kanji"` / `"Binary"`。`"Auto"` にはなりません（解決後の値です）。`"Binary"` は、STD-42のどの形式としても読めなかったことを示します（数字フォーマットは16符号すべてを写像するため、放置するとどんなペイロードも「それらしい数字列」になってしまいます）。この場合 `text` は空で、ペイロードは `raw_hex` に入っています。 |
| `byte_order`          | string  | 漢字時 | `"Normal"` または `"Swapped"`。どちらのシフトJISバイト順で正しくデコードできたか。**`format` が `"Kanji"` のときのみ**存在します。 |
| `text`                | string  | はい  | デコードしたメッセージ（UTF-8）。トーンのみの呼出しでは空文字列。 |
| `interpretation`      | string  | いいえ | 事業者固有の数字レイアウトを認識できた場合の可読表現。例: `Time broadcast: 2026-08-27 01:03 JST (Thu)`。該当しない場合は省略されます（RCR STD-42が規定するものではなくローカルな慣習なので、通常は省略されます）。生の文字列は常に `text` に入っています。 |
| `chars`               | number  | はい  | デコーダが生成した文字数（置換文字を含む）。 |
| `double_byte`         | number  | はい  | そのうちシフトJIS2バイト文字だった数。数字・カナ英数字形式では常に0。 |
| `header_bytes`        | number  | いいえ | 本文に到達するまでに読み飛ばしたバイナリヘッダのバイト数。ペイロードの先頭が本文でなかった場合のみ存在します（同報の放送文はバイナリヘッダの後ろに置かれます）。`raw_hex` にはヘッダを含む全体が入っています。 |
| `invalid`             | number  | はい  | マッピングできず U+FFFD を出力した文字数。それ以外は正常な呼出しでこの値が0でない場合、形式やバイト順を手動で誤って固定している可能性が高いです。 |
| `message_codewords`   | number  | はい  | この呼出しで受理したメッセージコードワード数。 |
| `corrected_bits`      | number  | はい  | 呼出し全体でBCHが訂正したビット数の合計。この値の増加は信号劣化の最も早い兆候です。 |
| `bad_codewords`       | number  | はい  | 訂正不能（3ビット以上の誤り）として破棄したコードワード数。0でなければ `text` に欠落があります。 |
| `payload_bits`        | number  | はい  | 収集した生メッセージビット数。`20 × message_codewords` に等しくなります。 |
| `raw_hex`             | string  | はい  | §3.6の規定どおり（各文字フィールドをLSB先頭で）バイトに詰めた生ペイロード。小文字16進、区切りなし。1バイトに満たない端数ビットは捨てられます。トーンのみの呼出しでは空文字列。 |

`raw_hex` はデコード前のペイロードです。漢字形式の場合はバイト順補正を行う**前**の
シフトJISバイト列なので、プラグインの形式判定やバイト順判定に同意できない場合は
ここから再デコードできます。下の漢字の例では `raw_hex` が `82b1 82bf 82e7` で
始まっており、これはシフトJISの「こ」「ち」「ら」です。

## 例

漢字の同報放送（見やすさのため折り返していますが、実際は1行です）。

```json
{"rx_time_ms":1774523412345,"rx_time":"2026-03-26T14:30:12.345Z",
 "address":1234567,"function":3,"function_label":"D","frame":7,
 "baud":1200,"inverted":false,
 "format":"Kanji","byte_order":"Normal",
 "text":"こちらは防災行政無線です。ただいま試験放送を行っています。",
 "chars":29,"double_byte":28,"invalid":0,
 "message_codewords":24,"corrected_bits":2,"bad_codewords":0,
 "payload_bits":480,
 "raw_hex":"82b182bf82e782cd96688dd08d7390ad96b390fc82c582b7814282bd82be82a282dc8e8e8cb195fa919782f08d7382c182c482a282dc82b78142"}
```

数字フォーマットの呼出し。

```json
{"rx_time_ms":1774523500000,"rx_time":"2026-03-26T14:31:40.000Z",
 "address":4242,"function":0,"function_label":"A","frame":2,
 "baud":512,"inverted":false,
 "format":"Numeric","text":"0123456789",
 "chars":10,"double_byte":0,"invalid":0,
 "message_codewords":2,"corrected_bits":0,"bad_codewords":0,
 "payload_bits":40,"raw_hex":"1032547698"}
```

## エンコーディング

レコードはUTF-8です。テキストはUTF-8バイトのまま出力します（JSON文字列として妥当
です）。エスケープするのは `"`、`\`、およびC0制御文字のみです（`\n`、`\r`、`\t`、
その他は `\u00XX`）。非ASCII文字を `\u` エスケープすることはないため、受け側は
ASCIIではなくUTF-8として読む必要があります。

## ストリームの利用例

```sh
# ファイルシンク
tail -f ~/.config/sdrpp/rcr_std42/decoded.jsonl | jq -r '"\(.rx_time) [\(.address)] \(.text)"'

# TCPシンク
nc 127.0.0.1 7356 | jq -c 'select(.bad_codewords == 0) | {rx_time, address, text}'
```

TCPシンクはクライアントごとに最大2048レコードをキューし、読み出しが滞った
クライアントには古いものから破棄します。そのため、詰まった受信側がデコーダや他の
クライアントを止めることはありません。待ち受けはループバックインタフェースのみです。
